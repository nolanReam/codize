# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Codize is an educational platform that helps students understand the projects they build with AI — it teaches real dev workflows and reasoning about your own code, using AI as a tool rather than a crutch. It is a benign educational product about architecture understanding and project reasoning. It is **not** a cybersecurity, exploit, malware, or offensive-security tool.

**Product direction (v3, reset 2026-07-03 after M12):** Codize is an **AI coding workflow trainer / Project Defense Workflow** — it helps student builders escape the 80% trap, use AI tools deliberately, verify what AI generated, and defend the projects they ship, via the Codize Build Loop: **Plan → Prompt → Generate → Review → Verify → Explain → Commit/Reflect**. The old "roadmap + checklist + gate + progress dashboard" framing is **incomplete** (those systems support the loop; they are not the product). **`docs/context/codize_product_vision_v3.md` is the current product-direction source for M13+**; `docs/context/codize_master_spec_v2.1.md` still controls backend invariants, intake, archetypes, security, RLS/auth, and gate mechanics (conflict resolution: `docs/context/context_authority.md`). **M13 is the AI Workflow Workspace MVP** — landing page (80% Trap), Project Cockpit, Prompt Builder, Review Board, Evidence Panel, Verification Lab, Evidence-Based Gate, Project Defense Report / Evaluation Summary — NOT the old generic intake-form/roadmap-page/checklist/gate-modal frontend plan (existing backend routes may be reused, but UX language and flow follow v3; the new v3 surfaces have no backend yet — see `.claude/memory/product-vision-v3.md`). Out of scope for v0.1: browser IDE, full GitHub OAuth, AI news, community/social, tool marketplace (manual evidence is acceptable).

The FastAPI backend lives in `backend/app/` (see `backend/README.md`): app factory + CORS + consistent error shape (`main.py`, `core/errors.py`), centralized `Settings` with SecretStr server-only values (`core/config.py`), Supabase JWT verification via JWKS/ES256 (`core/security.py`), and the `require_user` auth dependency → 401 (`deps/auth.py`). The template engine (`services/template_service.py`) loads and validates the three archetype templates at startup (fail-fast; rejects any fourth archetype), serves them as copies (no runtime mutation), and holds the spec's deterministic classification tiebreaker (`resolve_archetype`). The intake engine (`services/intake_service.py`) holds the five spec-verbatim questions, enforces sequential first-answering (Q1 unskippable; since M13E.1 an already-answered question may be revised until completion — classification always runs on the final stored answers), normalizes answers, stores them on the `projects` row via the `ProjectRepository` seam (`services/project_repository.py` — PostgREST with the service-role/secret key, every query ownership-filtered by `user_id`; **live writes verified end-to-end in M9** with the newer `sb_secret_...` key format, which the backend treats as opaque; the module also holds the `GateSessionRepository` since M9), and on completion classifies the project via a deterministic keyword fallback into `resolve_archetype` (the temp-0 LLM classification call replaces `_derive_classification_signals` in a later milestone). All LLM traffic goes through the provider-agnostic `services/llm_service.py`: Gemini primary (`GEMINI_API_KEY`/`GEMINI_MODEL`), OpenRouter fallback (`OPENROUTER_API_KEY`/`OPENROUTER_MODEL`), deterministic stub only for tests/no-key mode — **Anthropic is intentionally not supported**. The roadmap engine (`services/roadmap_service.py`) requires completed intake + archetype, fills the `roadmap_generation.md` prompt with the archetype template and verbatim intake answers, calls the LLM at temperature 0.7, validates the output against the source template and **fails closed on any structural drift** (phase count/order/numbers/titles, gate targets, gate depth, unlock conditions, AI/human task counts, verbatim NOTE:/RLS-first security constraints, archetype id), then persists the roadmap JSONB and flips `projects.status` 'intake' → 'active' in the same write; **live Gemini generation verified in M8** (4 real calls: 3 clean roadmaps, 1 drifted output correctly discarded by the fail-closed validator). **M13C.1B (2026-07-04) — roadmap reliability hotfix:** drift/failure no longer blocks the user. `generate_roadmap` makes one LLM personalization attempt; on provider error, unparseable output, or structural drift it falls back to `build_fallback_roadmap` — a deterministic, structurally-valid roadmap built straight from the archetype template (intake purpose substituted into the template's `[PROJECT_PURPOSE]`/`[PROJECT_SCALE]` slots, which live only in personalizable fields, so it always passes the **unchanged** validator; re-validated before storage). Invalid LLM output is still never stored; the fallback is silent-but-logged; temperature stays 0.7. Live-verified with real Gemini (4 runs: 2 personalized, 2 fallback, all → active/valid/7-phase, zero blocks). A stronger `GEMINI_MODEL` can be set via env to raise the personalization rate (provider-agnostic; no paid model hardcoded). OpenRouter fallback still live-unverified since Gemini never failed. The phase workspace (`services/phase_service.py`) serves phases straight from the stored roadmap (no LLM call — `phase_explanation.md` prose is deliberately not wired up yet); eligibility is intake complete + archetype + roadmap + status 'active'; task completion lives in the separate `projects.task_progress` JSONB column (`{"<phase>": ["ai-1", "human-2", …]}`, 1-based ids into the phase's task lists) so ticking tasks can never mutate the fixed roadmap structure, unknown ids are dropped on read, and `current_phase` is advanced only by the Interrogation Gate, never by task completion. The Interrogation Gate (`services/gate_service.py`, M9) runs the spec's 3-turn flow for the current phase: eligibility + 30-minute cooldown check (derived from `gate_sessions.failed_at`, no cooldown table), then anchor collection (deterministic server-side concrete-element check plus model re-validation via an `ANCHOR_REJECTED:` marker — no Turn 1 question is ever generated without a valid anchor), then turns 1–3 at temperature 0.3 (`gate_turn_1/2/3.md`; each turn stores the previous answer and the next question in one write so LLM failures are retryable with nothing lost), then a **separate temperature-0 evaluator call** (`gate_evaluation.md`) parsed strict/fail-closed (malformed verdict → 502, nothing stored). On PASS: `passed_at`, `gate_history_summary` appended (attempt counts only — no scores, the column is client-readable), `current_phase` +1 but never past the final phase. On FAIL: `failed_at` (starts the cooldown), no advancement. The 0–10 quality score is stored on `gate_sessions.score` for the hidden unlock thresholds and **never appears in any API response** (the DB also revokes the column from client roles). **Live-verified in M9 with real Gemini**: one full PASS gate (implementation-specific hypothetical, phase advanced 1→2) and one full FAIL gate (textbook answer auto-failed Condition 3, cooldown enforced live), plus the spec's 10 live adversarial prompt cases — all defended after two prompt strengthenings recorded in `docs/prebuild/adversarial_tests.md` (re-runnable via `scripts/live_adversarial_tests.py`). The functional unlock engine (`services/unlock_service.py`, M10) implements the spec's variable-reward mechanic with **no schema change** (the M2 `unlocks` table already fit): after every gate PASS (never a FAIL) the gate flow evaluates unlocks by recomputing from the project's passed-gate history — the hidden rule (spec's resolved decision) is a quality score ≥7 on **two consecutive phases' passed gates** (only the passing attempt's score counts; a single high score never qualifies; phase 1 alone never qualifies), and qualifying at phase N grants roadmap phase N's `functional_unlock` reward (template content: skip-configuration / pre-built component — the spec's two MVP example types). Grants are idempotent and self-healing: recompute-then-insert-missing plus the DB's unique `(project_id, unlock_key)` with PostgREST `resolution=ignore-duplicates`, and an unlock storage error never fails the PASS response (logged; the next PASS backfills). Unlocks never mutate the roadmap and never advance phases; the threshold, rule, and raw scores are server-only and appear in no response — client views carry only id/unlock_key/phase/description/unlocked_at/project_id (the `unlocks` table is owner read-only, client writes revoked since M2). **Live-verified in M10** (10/10 smoke checks): real grant after scores 8,7 on consecutive phases, idempotent re-evaluation, duplicate insert ignored by the constraint, RLS client reads (owner sees own row with no score field, other user sees zero). The reconnection engine (`services/reconnection_service.py`, M11) implements the spec's 72-hour Yeager mechanic server-side with **no schema change**: `profiles.last_login_at` means **"last acknowledged presence"** — initialized by the signup trigger's `default now()` (a brand-new user never sees the modal) and written ONLY by `POST /reconnection/acknowledge`; `GET /reconnection` is a pure read, so checking state can never suppress the modal (frontend contract for M13: GET first on every login, then acknowledge — immediately when not needed, on the "Let's keep building" click when needed). The GET returns one of four controlled 200 states: `new_user`, `recently_active` (< 72h), `workspace_not_ready` (away 72h+ but no active project/roadmap yet), or `reconnection` (away 72h+) with a deterministic LLM-free safe summary — the verbatim intake purpose (spec requirement), current phase number/title/core-concept reminder, incomplete current-phase tasks, the newest gate-history line (attempt counts only), earned unlock views, and a recommended next action; never scores, thresholds, prompts, or keys. Reconnection never mutates the roadmap, never advances phases, never grants unlocks. **Live-verified in M11** (12/12 smoke checks: trigger-fresh timestamp → recently_active, backdated 100h → workspace_not_ready then full reconnection summary, idempotent acknowledge, per-user isolation, RLS profile reads with real JWTs). The evaluation engine (`services/evaluation_service.py`, M12) is a **deterministic, computed-on-read progress evaluation** — no LLM call, no persistence, no schema change (the spec defines no evaluation snapshot to store, and its tracking section forbids showing process metrics as numbers/scores): `GET /evaluation` returns one controlled 200 state — `not_started` / `intake_needed` / `roadmap_needed` pre-active, then `in_progress`, `gate_ready` (all current-phase tasks done, or a gate session mid-flight → resume), `cooldown` (reuses `gate_service.cooldown_remaining`, public since M12, and adds `cooldown_seconds_remaining`), or `complete` (final phase's gate passed) — never an error. Content comes only from already-client-visible state via the shared safe-view seams (`phase_service.current_phase_view` + the new public `phase_service.incomplete_tasks`, `unlock_service.unlock_views`): phase number/title, completed/total phase and task counts, incomplete tasks, a `recent_gate` label (newest `gate_history_summary` line for passes — attempt counts only — or the evaluator's already-client-visible one-sentence reason for fails; never a score), earned unlock views, and a recommended `next_action`. Evaluation is a pure read: it never mutates roadmap/tasks/gates/unlocks, never advances phases, and never touches `last_login_at` (it takes no ProfileRepository at all). **Live-verified in M12** (12/12 smoke checks: full lifecycle state walk, live task tick reflected, consecutive-quality unlock surfaced safely, cooldown after a FAIL, leak-free JSON, pure-read row comparison, per-user isolation). The workflow artifact store (`services/workflow_service.py`, M13B) persists the four student-authored v3 Build Loop sections — `prompt_builder`, `review_board`, `evidence`, `verification` — phase-scoped in the `projects.workflow_artifacts` JSONB column (migration `20260703130000`, exact `task_progress` precedent: outside the roadmap jsonb, owner RLS + table-level grants inherited, no new policies). **Storage only**: no LLM anywhere in the module, a write patches exactly the one column (roadmap/task_progress/gates/unlocks/reconnection unreachable by construction), the gate does NOT read these artifacts (evidence-aware gate prompts remain a future spec-guardian-gated change), and the Project Defense Report stays client-assembled in M13C — no report endpoint. `PUT` is an idempotent full-section replace stamped with a server-side `saved_at`; payloads are validated fail-closed (`schemas/workflow.py`: extra fields forbidden, string/list caps, http(s)-URL and 7–40-hex commit-hash checks on evidence kinds, fixed 8-item verification-check enum, 30 KB total-section cap, and secret-looking content rejected — `sb_secret_`/`sk-or-`/`AIza`/PEM markers); unknown stored keys are dropped on read. M13B also added `"PUT"` to the CORS allow_methods (first PUT route) and made `phase_service.require_phase` public. **Live-verified in M13B** (11/11 smoke checks: live column default on a pre-existing row, four-section round-trip through the real repository, full-section replace + phase isolation, rejected payloads stored nothing, live row-diff touched only `workflow_artifacts`, owner RLS read of the new column with a real JWT, zero cross-user visibility, leak-free client payload). ## Planned architecture

Built strictly back-to-front through external services — **never Frontend → External Service directly.**

- **Frontend (Next.js, deployed on Vercel) → Backend (FastAPI, deployed on Railway) → External Service (Supabase, LLM provider APIs).**
- **Supabase** for database + auth. **FastAPI** (async — required, every LLM call is I/O-bound) for the API. **Gemini (primary) / OpenRouter (fallback)** for the AI engines via the provider-agnostic `llm_service`; Anthropic is intentionally not supported.
- Backend structure: a **`services/` layer holds all AI calls, gate logic, and template loading — never in route handlers.** A `templates/` folder holds the three archetype JSON files, loaded at startup.
- MCP tooling is available for filesystem, git, github, supabase, and playwright — use the supabase MCP to *verify* schema/RLS rather than assuming.

## Build order & milestone workflow (important)

Do not build the whole product in one session. Work **exactly one milestone at a time.**

**Pre-build gate (spec "Pre-Build Artifacts Required"):** before *any* backend/schema code, both must exist —
1. The **three archetype JSON templates** (full phase structure for all three archetypes).
2. The **six system prompts** (per the spec's "System Prompt Architecture"), drafted in full and manually tested against adversarial inputs.

After the pre-build artifacts, a reasonable milestone sequence (derived from spec Section 5 in-scope items) is: Repository foundation → Supabase schema + RLS → Auth → FastAPI core → Archetype template engine → Intake → Roadmap generation → Phase workspace → Interrogation Gate → Functional unlocks → Reconnection → Evaluation → **AI Workflow Workspace MVP (M13 — reframed from "frontend integration" by the v3 vision reset; see `docs/context/codize_product_vision_v3.md`)** → Security audit → Deployment (Vercel + Railway).

For each milestone: **Implement → Test → Verify → Commit → Update memory → Stop.** Then output `MILESTONE COMPLETE` with files changed, tests run, verification results, and the git commit hash, and instruct the user to `/compact`, start a fresh session, and paste the continuation prompt. Do **not** auto-continue into the next milestone.

Maintain lessons in `.claude/memory/` (one specific lesson per file; update or remove stale ones); consult it before major architectural decisions.

## Domain invariants that must not drift

Fixed by the spec — do not add, remove, or reorder:

- **Intake:** exactly five mandatory, sequential, conversational questions. Question 1 is verbatim "What problem do you want to solve, and who does solving it help?" and cannot be skipped. Store all five answers (purpose, scope, stack, self-assessed understanding, timeline). Signup goes straight to question 1 — no form/dashboard/homepage.
- **Archetypes:** exactly three — (1) AI-Powered App, (2) REST API Backend, (3) Full-Stack Web App. No fourth, ever. Structure comes from hardcoded JSON templates; the LLM personalizes wording only and may never add, remove, or reorder phases, change AI-vs-human task labels, or alter gate targets/unlock conditions. Classification is a temperature-0 call. Tiebreaker: LLM API is a core feature → Archetype 1; else has frontend/database → Archetype 3; else → Archetype 2. Default stack for Archetype 1 is fixed: Python + FastAPI + Vanilla HTML/JS.
- **Interrogation Gate:** mandatory, cannot be skipped (student may choose Option A explanation / Option B bug-hunt format; A is the MVP default). Requires a self-reported anchor statement, then Turn 1 (implementation-specific question, temp 0.3), Turn 2 (probe the weakest of accuracy/specificity/completeness), Turn 3 (fresh hypothetical from anchor + prior answers + implementation, not answerable from generic knowledge). On failure: no immediate retry, **30-minute cooldown**.
- **Evaluation:** a **separate** LLM call at **temperature 0**, binary PASS/FAIL + one-sentence reason + a 0–10 quality score, against three conditions (Structural Identification, System Ripple Effect, Implementation Specificity — all three required). **Auto-fail any textbook/generic answer** that could apply to any codebase regardless of technical correctness.
- **Gate eval is a two-call pattern:** Call 1 (temp 0.3) generates the Turn 3 hypothetical; Call 2 (temp 0) evaluates the answer. (Phase explanations use temp ~0.7.)
- **Functional unlocks:** triggered by performance thresholds the student cannot observe (e.g. quality score ≥7 across two consecutive gates), never by phase completion. No badges/XP/streaks/leaderboards.
- **Reconnection:** in-app modal only (no email). Triggers on login when `last_login` delta > 72h; shows the student's verbatim intake purpose; dismissed only by clicking "Let's keep building" (no timer, no click-outside, no Escape).

## Security constraints (non-negotiable)

Encoded into every archetype template from Phase 1, not bolted on at the end:

- **Secrets stay server-side.** Never expose LLM provider keys (Gemini/OpenRouter), Supabase service-role keys, or DB secrets to the frontend — `.env` values get bundled into JS. Frontend calls the backend; the backend calls external APIs with the real key. (OWASP A02.)
- **RLS on every Supabase table before any other DB code.** Each table has a `user_id` column and an ownership policy (`USING (auth.uid() = user_id)`). "User is logged in" is not ownership. Verify with the supabase MCP. (OWASP A01.)
- **Auth enforced server-side on every protected endpoint** — UI hiding/redirects are not security. Return 401 unauthenticated, 403 for another user's resource. (OWASP A01.)
- **Input validation** (parameterized queries, output escaping) on any user input reaching the DB or the UI. (OWASP A03.)
- Every archetype ends with a mandatory, gate-checked **pre-deployment security checklist** phase.
- At each milestone, run a living audit of tables, policies, and ownership checks; record findings. Advanced hardening (rate limiting, DDoS, full OWASP audit, pentest, CSP) is explicitly out of scope for the MVP.

## Engineering style

Build the simplest robust thing that satisfies the current task — no speculative abstractions, premature optimization, hypothetical scaling layers, or future-proofing. Trust framework guarantees; validate only at system boundaries (user input, external APIs). Escalate reasoning effort only for gate logic/prompts/rubrics, security audits, and evaluation systems.

Before adding anything, check it against the spec: is it explicitly required, is it needed for the current milestone, can it be done more simply? If no, don't build it. The "temptation to add a fourth archetype will come — resist it."

Report only verified work: audit each completion claim against actual test/tool/MCP output. If something is unverified or failed, say so — never fabricate progress.
