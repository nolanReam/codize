# Codize Learning Model v1

> [!WARNING]
> **Status: Historical V1 learning reference — not V2 teaching-policy authority.**
>
> Its distinctions between workflow activity, student judgment, evidence, and learning remain useful. Its eight-competency vocabulary, phase/workflow binding, and bounded-assignment slice are not mandatory V2 design. A V2 Learning / Teaching Policy has not yet been accepted.

**Former status:** Active educational-design authority
**Scope:** Learning design only; subordinate to current architecture, safety,
ownership, lifecycle, provenance, trust, and implementation truth.

## Purpose

Codize is guided practice for AI-assisted software judgment. Students learn by
making real decisions inside the project workflow, using an external AI tool,
and inspecting and explaining the result. Codize supplies structure,
just-in-time principles, bounded examples, transparent checks, and revision
paths. It does not write the student's answer or convert workflow activity into
proof of learning.

## Competency names

The eight competency names are:

1. Assignment decomposition
2. Prompt construction
3. Context selection
4. Guardrail setting
5. Change interpretation
6. Review judgment
7. Verification and evidence judgment
8. Implementation explanation

These are design categories, not a global score or public profile.

## Distinct records

- A **project task** is roadmap work that changes or decides something in the
  project.
- A **learning objective** names the judgment the student is practicing.
- A **workflow action** is an action such as saving a Prompt, Review decision,
  result, Evidence record, or Defense response.
- **Learning evidence** is a bounded student performance that can support a
  careful educational inference.

Completing a workflow action, saving an artifact, checking a build task, or
advancing a phase is not automatically learning evidence.

## Learning principles

- The student owns the boundary, wording, context, guardrails, inspection,
  testing, evidence, and explanation.
- Teaching appears just in time beside the real decision. Codize does not
  front-load a separate course.
- Productive difficulty is preserved: structure may reduce blank-page work,
  but Codize does not generate the final answer.
- Feedback must state exactly what it checked. Presence checks are not semantic
  judgments.
- Future support may become competency-specific and reversible. It must never
  become one global mastery score, a permanent label, or an automatic lowering
  of standards.
- Transfer requires changed conditions. Repeating the same scaffolded action
  is not enough to claim transfer.

## First bounded slice: M18C.1

M18C.1 implements one objective:

> Keep one AI request bounded and checkable.

For a new Prompt bound to a current AI-owned assignment, the student states a
finish condition, excluded work, and an observable inspection condition.
Codize deterministically checks that those required pieces are present and
valid, then lets the student apply their own words to editable Prompt fields.
It adds no provider evaluation, score, mastery, adaptive fading, learning
analytics, completion inference, or additional route.

Later validation may compare this first attempt with a varied assignment under
equal or reduced visible support. That is a research seam, not implemented
product behavior in M18C.1.
